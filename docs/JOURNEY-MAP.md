# Journey Map — every route through Takeoff Tooling

The UX counterpart to [ARCHITECTURE.md](ARCHITECTURE.md) and the sibling of Count
Tooling's `JOURNEY-MAP.md`: a single decision document for making Takeoff Tooling
**easy to understand for most users** while keeping the spirit of a simple electrical
takeoff-and-pricing tool. The organizing unit is the **journey** — a route a real
estimator takes to get something done — not the feature. Every audit, verdict, and
improvement hangs off a journey.

The frame below reuses Count Tooling's vocabulary verbatim (personas, spirit test,
verdicts, severities, dossier template, phases) so the two programs read as one and
findings can be compared across apps — especially on the hand-off journey (J2 here,
J11 there), which spans both.

## The spirit test

Every proposed change must pass ALL four, or it dies in synthesis:

1. **Fewer steps or fewer decisions** on the estimator's happy path — not just different ones.
2. **Trade language, not software language** ("run", "fixture", "homerun", "overage",
   "supply house", "quote" — not "child item", "temp buffer", "fill target").
3. **A simplicity budget** — the proposal states what it *removes or makes unnecessary*.
   A proposal that only adds surface is rejected by construction.
4. **Findable by an electrician who has never read a guide.** If the answer is "it's in
   the docs", the verdict is `teach`, not a UI change.

## Verdict vocabulary

| Verdict | Meaning |
|---|---|
| **keep** | Already simple — document it as-is (dossier → knowledge base / guide / sales) |
| **polish** | Small affordance, label, default, or empty-state change |
| **rework** | The flow itself needs restructuring |
| **teach** | App is fine; the guide, an in-app hint, or onboarding must carry it |
| **hide** | Confusing surface for most users — demote behind a role gate / menu |
| **gap** | A route users expect that does not exist |

Friction severity: **blocker** (users stop / do it wrong) · **stumble** (users recover
but lose time or confidence) · **papercut** (annoyance; costs polish, not outcomes).

## Telemetry visibility

Every rework ships its own event (X17, landed): one `TakeoffEvents.log(name, props)` line at
the moment the journey turns, named in the row that proposed it, so the next re-rank reads
measurements instead of judgement. The first set is `session_start`, `flow_saved`,
`book_add_to_target`, `import_added`, `purchase_list_generated`, `pdf_exported`,
`share_link_created` / `share_link_opened`, `project_switched` and `undo` — the full list,
with props and insertion sites, is in [ARCHITECTURE.md](ARCHITECTURE.md) → Telemetry.
Events carry **structure only**: counts, booleans, short enums, durations, the viewport
width and whether the pointer is coarse, plus an anonymous per-install id and — only while
signed in — the user id. No description, job or client name, per-row price, email or search
term may appear in a prop; the sanitizer in `js/events.js` drops them whatever a call site
passes, and `takeoff-telemetry-off` (or Do-Not-Track) silences the whole thing. A dossier's
**Evidence** line therefore stops reading "telemetry: none yet" as soon as its journey's
event has shipped and one window of data has landed; until then it must still say so.

## Phase 1 findings-in-advance (from the 2026-09-06 walks)

Things Phase 1 would otherwise discover, recorded now so the ground-truth agents start
from them rather than re-derive them:

- **Zero telemetry.** Takeoff Tooling has no `logUserEvent` equivalent; Supabase holds
  data tables only (`takeoff_store`, `takeoff_projects`, `takeoff_suggestions`,
  `takeoff_profiles`). Every journey is blind. Standing rule, borrowed: **every rework
  ships with its own event**, and Phase 1 should propose the minimal event set
  (candidates: `import_added`, `flow_saved` with flow kind, `book_add_to_target`,
  `quote_recorded`, `pdf_exported` with variant, `share_link_created`, `project_created`).
- **Surface scale is small and knowable**: 4 views, 11 modals, ~34 nodes
  ([journeys/_surfaces.md](journeys/_surfaces.md)). The simplification target is not
  surface count (Count Tooling's problem) but **numeric trust** — three of the seven
  blocker-grade findings on 2026-09-06 were wrong dollar figures (purchase list vs
  summary, $0 overage, dropped import quantities). Walkers should carry a calculator.
- **Duplicate-surface moments to watch**: manifest book icon vs flow-row book icon vs
  "PB" fill button (three ways into the book with different targeting); type chip vs
  "Add" button vs hotkey; header "Labor & Price Book" vs row icons.
- **Cross-cutting themes** likely to deserve shared treatment in synthesis: (a) **where a
  number comes from** (parent vs children labor, extended vs unit, overage pricing,
  provenance badges), (b) **the Count Tooling hand-off contract** (what `type` values
  arrive, what "overages only" means on both sides), (c) **role visibility** (what an
  estimator vs admin sees; the `[hidden]`-attribute class of bug).
- **Guides don't exist yet** — README.md is the only user-facing doc. `teach` verdicts
  therefore land in a Phase 5 backlog for a first guide set, not edits to existing articles.

## Dossier template (`docs/journeys/<slug>.md`)

Identical to Count Tooling's so dossiers can be read side by side; the copy lives in
[journeys/_TEMPLATE.md](journeys/_TEMPLATE.md).

```
# J<N> — <Title>
Personas · Trigger ("what just happened in the estimator's world")
## Entry points         — every way in: header / row control / hotkey / modal / hash route
## Current route        — numbered steps as actually walked; screenshots in journeys/img/;
                          step count + decision count; divergences from the docs
## Naive attempt        — a first-timer's discovery path, before reading anything
## Evidence             — telemetry (none yet — say so), README/guide coverage, spec coverage
                          (*.spec.js / *.test.js), modals touched, hotkeys, storage keys
## Friction findings    — table: # · severity · what happens · why it hurts · verdict stamp
## Proposals            — each with verdict + the four spirit-test answers
## Guide actions        — what a first guide article must carry (Phase 5 backlog)
## Demo moment          — the ≤10-second thing that sells this journey
```
